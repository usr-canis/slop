Garbage collection inside a UFS device

NAND flash cannot overwrite data in place. Every rewrite leaves a stale copy behind, and the controller has to keep reclaiming that space without the phone noticing. This is how it does it, what it costs, and which knobs the host has.

01 · Physics first

The three NAND rules that make GC necessary

A UFS device is a small computer: a controller (CPU, SRAM, ECC engine, UniPro/M-PHY link) wired to one or more NAND flash dies. NAND has a strict hierarchy and three rules that the rest of this page follows from.

RuleWhat it meansConsequence
1. Erase before writeA programmed page cannot be reprogrammed. It must be erased first.No in-place overwrite. Updated data always goes to a fresh page.
2. Erase is per block, program is per pageYou can write 16 KiB at a time but can only erase several MB at a time.A block with even one live page cannot be erased until that page is moved somewhere else.
3. Erases wear the cells outEach program/erase (P/E) cycle damages the oxide. Rough budgets: SLC tens of thousands, TLC around a few thousand, QLC around a thousand (vendor-specific).Every unnecessary copy costs lifetime, so GC has to be efficient and spread evenly (wear levelling).
02 · The translation layer

The FTL hides NAND behind a simple block device

The host (Linux, Android) sees a UFS logical unit as a flat array of 4 KiB logical blocks, addressed by LBA, and talks to it with SCSI commands such as WRITE(10), READ(10) and UNMAP. It believes it can overwrite LBA 2 whenever it likes.

The firmware's Flash Translation Layer (FTL) makes that illusion work. Its central structure is the logical-to-physical (L2P) map: for every LBA, which physical page (PPN) holds the current copy. When the host rewrites an LBA, the FTL writes the new data to a free page, updates the map, and marks the old page invalid. That is an out-of-place update.

Why the map is a big deal on UFS

With page-level mapping at 4 KiB granularity and about 4 bytes per entry, the map is roughly 1/1000 of capacity: about 256 MB of map for a 256 GB device. SSDs often keep this in on-board DRAM. UFS controllers are DRAM-less to save power and board space, so the full map lives in NAND and only a small working set is cached in controller SRAM. A map-cache miss costs an extra NAND read. This is the problem HPB later tries to solve (section 10), and it matters for GC because every page GC moves needs a map update.

03 · The mechanism

One garbage collection cycle, step by step

Out-of-place writes keep consuming free (erased) blocks. The controller keeps a free block pool. When it drops below a threshold, GC reclaims space by taking a block full of stale pages and turning it back into an erased block.

  1. Select a victim. Choose a closed (fully written) block, usually the one with the fewest valid pages (section 6).
  2. Migrate valid data. Read each valid page, check and correct it with ECC, and program it into a GC destination block. Controllers usually use copy-back or on-die buffers to avoid shipping data over the internal bus twice, but the program is still a real NAND write.
  3. Update the L2P map for every moved LBA, and persist those map changes.
  4. Erase the victim, increment its erase count, and return it to the free pool.

GC is also the vehicle for other housekeeping that moves data for reasons other than free space: static wear levelling (moving cold data off low-wear blocks), read-disturb refresh (rewriting blocks read very many times), retention refresh (rewriting data that has aged), and bad-block retirement. Vendors often lump all of this under "background operations".

04 · The cost

Write amplification: what GC costs you

The write amplification factor (WAF) is the ratio of bytes actually programmed into NAND to bytes the host asked to write. A WAF of 1 means no GC copies at all. A WAF of 4 means that for every 1 MB an app writes, the flash programs 4 MB, so it wears 4× faster and its effective write bandwidth is roughly divided by 4.

If GC always reclaims blocks that are a fraction u valid, then each cycle copies u·P pages to free (1−u)·P pages for new host data:

WAF = (host pages + copied pages) / host pages = ((1−u)·P + u·P) / ((1−u)·P) = 1 / (1 − u)
WAF2.50

The curve is brutal near the top. Going from 50% to 75% valid doubles the cost (WAF 2 → 4). Going from 75% to 90% more than doubles it again (WAF 4 → 10). Everything else on this page (over-provisioning, TRIM, victim selection, hot/cold separation) is about keeping u low.

Two further effects stack on top. The file system can amplify writes itself (journals, metadata, f2fs's own segment cleaning), and a WriteBooster flush rewrites SLC-cached data into TLC, which is an extra internal write of its own. End-to-end WAF on a phone is the product of these layers.

05 · When it runs

Foreground GC vs background GC

Foreground · on demand

Foreground (synchronous) GC

Triggered when a host write arrives and the free pool is at or below its minimum. The controller has to reclaim space before or while serving that write, so GC work is interleaved with host commands. The host sees it as latency spikes (tail latency, p99/p99.9) and lower throughput. Unavoidable when the device is kept busy with no idle time.

Background · idle time

Background GC (BKOPS)

The controller reclaims space while the host is idle, building the free pool back up so that later bursts are served at full speed. In UFS this is Background Operations (BKOPS), controlled by the fBackgroundOpsEn flag and reported through bBackgroundOpStatus. It needs power and time: if the host powers the device down or puts it in deep sleep immediately, BKOPS cannot run.

Real controllers blend the two. Many run a little opportunistic GC on their own whenever the command queue is empty for a few milliseconds, escalate to foreground GC only when the free pool is critical, and use host-permitted BKOPS for the longer tasks.

06 · Choosing what to clean

Victim selection policies

The policy that picks the victim block decides u, and so decides the WAF. Vendors keep their exact algorithms private, but they are built from these classic ideas.

PolicyPicksStrengthWeakness
GreedyBlock with the fewest valid pagesLowest immediate copy cost; optimal for uniform random writesIgnores how soon data will die. A hot block about to be fully invalidated may get cleaned too early, and cold blocks can sit untouched forever (bad for wear)
FIFO / round-robinOldest written blockTrivial, naturally spreads wearWill happily copy a nearly full block; noticeably higher WAF
Cost-benefitMax of (1−u)·age / 2uPrefers old, mostly dead blocks; lets hot blocks "ripen" first. Better on skewed workloadsNeeds per-block timestamps and more CPU per decision
Windowed greedyGreedy among the k oldest blocksMiddle ground between greedy and FIFO; bounded search costTuning k is workload-dependent
Hot/cold separation(Placement, not selection) writes hot and cold data to different open blocksHot blocks die almost entirely, so victims have u ≈ 0. Biggest single WAF win on real workloadsNeeds a way to classify data: update frequency, GC-survival count, or host hints

GC copies are themselves a hot/cold signal: data that survived a GC is probably cold. Many FTLs send GC-migrated pages to a separate "cold" open block rather than mixing them with fresh host writes. On Android, f2fs helps from the host side by splitting its own logs into hot, warm and cold data and node segments.

07 · Spare room

Over-provisioning: hidden space that makes GC cheap

The device always has more physical NAND than it exposes. That spare is over-provisioning (OP). Because the host can never fill the spare, there are always invalid pages spread across the drive, which keeps the average victim's u below 100% even when the visible capacity is completely full.

For uniform random writes with greedy GC and large blocks, a well-known analytic approximation (Xiang & Kurkoski, 2012) relates WAF to the spare factor ρ = (physical − user) / user:

WAF ≈ (1 + ρ) / (2ρ)

Free space the host has TRIMmed counts as extra OP. A phone that is 60% full and issues TRIM properly behaves like a device with very generous over-provisioning. A phone that is 98% full has almost nothing but the factory spare left. This is the main reason a nearly full phone gets slow.

08 · Telling the device what's dead

TRIM / UNMAP: invalidating pages without writing

When you delete a file, the file system only updates its own metadata. The device has no idea those LBAs are now garbage: as far as the FTL knows, they are valid data that must be preserved and copied by every GC that touches them. TRIM fixes that. UFS is SCSI-based, so the command is SCSI UNMAP; Linux issues it as a "discard".

How Linux and Android send it

Online discard (-o discard): issued as files are deleted. f2fs batches these asynchronously in a discard thread, mostly during idle time.

Periodic trim (fstrim): walks free space and unmaps it in bulk. Android's idle maintenance runs this routinely when the phone is idle and charging.

Device side

A logical unit supports UNMAP when it is thin provisioned: bProvisioningType in its unit descriptor is set to a thin-provisioning value (with TPRZ deciding whether unmapped LBAs read back as zeros).

UNMAP is cheap: the FTL just clears map entries and drops valid counts. The space is physically recovered later, by GC.

A related operation, Purge (fPurgeEnable, status in bPurgeStatus), physically erases all unmapped data for secure deletion. It forces the GC work to happen right away and can take a long time.

09 · SLC cache

WriteBooster and how it interacts with GC

Introduced in UFS 3.1, WriteBooster uses part of the NAND in SLC mode (1 bit per cell) as a write buffer. SLC programs several times faster than TLC, so bursts (app installs, camera bursts, file copies) land at SLC speed. Later the device flushes the buffer into TLC.

InteractionWhat happens
Flush is GC-like workDraining the buffer is a copy from SLC to TLC. Data that is overwritten while still in SLC never needs flushing, which is a real WAF saving for hot data.
Flush needs idle timeEnabled by fWriteBoosterBufferFlushEn (explicit flush) and fWriteBoosterBufferFlushDuringHibernate (flush while the link is in Hibern8). If the host never allows either, the buffer stays full and every write falls back to TLC speed.
Buffer size can depend on free spaceIn "preserve user space" mode (bWriteBoosterBufferPreserveUserSpaceEn), the SLC buffer is borrowed from unused user capacity. As the phone fills, the buffer shrinks. A full phone loses both its OP headroom and its fast write cache at the same time.
SLC wears tooThe buffer takes many P/E cycles. bWriteBoosterBufferLifeTimeEst reports its wear, and the device can disable WriteBooster when it is worn out.
Status reportingbAvailableWriteBoosterBufferSize reports how much buffer is free (in 10% steps). dCurrentWriteBoosterBufferSize reports its current size. Buffer type is LU-dedicated or shared (bWriteBoosterBufferType).
10 · Map caching on the host

HPB (Host Performance Booster) and GC

Because a UFS controller can cache only a small part of the L2P map, random reads across a large footprint keep missing the map cache and need an extra NAND read. HPB (a JEDEC UFS extension, version 1.0 alongside UFS 3.1 and 2.0 later) lets the host keep L2P entries in its own DRAM. The host sends the physical address along with an HPB READ command, and the device can skip its own map lookup.

GC is the main thing that breaks this. Every page GC moves changes its physical address, so the host's cached copy goes stale.

Practical effect: heavy GC, for example on a full device under writes, makes HPB less effective, because more host-cached entries are stale and more reads fall back to the slow path. Mainline Linux added HPB support around kernel 5.15 and later removed it again; phones that use HPB generally rely on vendor kernel code. Treat exact kernel versions as something to check for your platform.

11 · What the host can control

BKOPS, exception events and the attributes that matter

The host cannot tell the device which block to clean. It controls when the device is allowed to do background work, and it can observe how urgent that work is. UFS exposes this through descriptors, flags and attributes read and written with Query Request UPIUs.

bBackgroundOpStatusMeaningTypical host reaction
00hNo background operations neededNothing
01hNeeded, not criticalAllow when convenient
02hNeeded, performance is being impactedEnable BKOPS; avoid immediate deep power-down
03hCriticalEnable BKOPS now; keep the device powered until the level drops
ControlTypeRole in GC
fBackgroundOpsEnFlagPermits the device to run BKOPS (GC, wear levelling, refresh) on its own while idle
bBackgroundOpStatusAttributeDevice's own estimate of how urgent the pending work is (table above)
wExceptionEventControl / wExceptionEventStatusAttributesHost can enable the URGENT_BKOPS exception event, so the device raises an alert in a response when BKOPS becomes urgent instead of being polled
fWriteBoosterEn, fWriteBoosterBufferFlushEn, fWriteBoosterBufferFlushDuringHibernateFlagsTurn on WriteBooster and allow its flush during idle or Hibern8
bAvailableWriteBoosterBufferSizeAttributeFree SLC buffer remaining; low values mean writes are about to slow down
bProvisioningType (unit descriptor)Descriptor fieldEnables thin provisioning so the LU accepts UNMAP
fPurgeEnable / bPurgeStatusFlag / attributeForces physical erase of unmapped data
bDeviceLifeTimeEstA/B, bPreEOLInfo (health descriptor)Descriptor fieldsWear consumed so far, the long-term consequence of WAF

How the Linux UFS driver uses them

The ufshcd driver supports "auto-BKOPS". Depending on the platform's capability flags, it either keeps fBackgroundOpsEn set except during suspend, or leaves it off and turns it on when the device reports bBackgroundOpStatus at or above an urgency threshold (by default "performance impacted"), including via the URGENT_BKOPS exception. During runtime suspend it checks the status and may hold the device powered so urgent BKOPS can finish. WriteBooster is enabled at init when supported, and its flush is typically allowed during Hibern8.

On a rooted device or dev board you can inspect these values through sysfs. Paths vary by SoC and kernel version:

# Background operations
cat /sys/bus/platform/drivers/ufshcd/*/attributes/bkops_status
cat /sys/bus/platform/drivers/ufshcd/*/flags/bkops_enable
# WriteBooster
cat /sys/bus/platform/drivers/ufshcd/*/flags/wb_enable
cat /sys/bus/platform/drivers/ufshcd/*/attributes/wb_avail_buf
cat /sys/bus/platform/drivers/ufshcd/*/attributes/wb_life_time_est
# Wear (health descriptor)
cat /sys/bus/platform/drivers/ufshcd/*/health_descriptor/life_time_estimation_a
# Host-side GC on f2fs (Android data partition)
cat /sys/fs/f2fs/<dev>/gc_urgent

Two garbage collectors stacked

Android's data partition usually runs f2fs, a log-structured file system that does its own segment cleaning (host GC) on top of the device's FTL GC. Both copy valid data to reclaim space, so their amplification multiplies. f2fs mitigates this by issuing discards for cleaned segments and aligning its sections with device erase units. Android also triggers f2fs GC during idle maintenance on recent versions. Zoned UFS, added to recent JEDEC specifications, goes further: the host writes zones sequentially and does the cleaning itself, which can largely remove device-side GC.

13 · Worked scenarios

Scenarios

A. A 95%-full phone under sustained random writes

worst case

Setting: a 256 GB phone with 12 GB free. A large game update or a benchmark issues random 4 KiB writes continuously for several minutes. The phase lengths below depend entirely on the device; the shape is typical.

  1. Burst phase (WriteBooster). Writes land in the SLC buffer at full speed. Because the phone is nearly full and the buffer may be in "preserve user space" mode, the buffer is small and fills quickly.
  2. Direct-to-TLC. Buffer exhausted; writes go straight to TLC. Throughput drops to native TLC speed. The free block pool is still draining.
  3. GC onset. The free pool hits its threshold. Foreground GC starts interleaving with host writes. Victims are mostly valid because only factory OP plus 12 GB of (hopefully trimmed) free space hold invalid pages. Latency spikes appear and throughput becomes jagged.
  4. Steady state. Host throughput settles near NAND write bandwidth ÷ WAF. With effective spare around 12% (7.4% factory plus about 5% trimmed free space), the greedy model gives WAF ≈ (1.12)/(0.24) ≈ 4.7, so the app gets about a fifth of the NAND's raw write bandwidth and wears the flash about 4.7 times faster than the bytes it writes.

Recovery: once the writes stop and the screen goes off, BKOPS and the WriteBooster flush rebuild the free pool and SLC buffer. The next burst is fast again, if the host gives the device the idle time (scenario B). Freeing space and letting TRIM run does more than anything else here, because it raises ρ directly.

B. An idle phone overnight

best case

Setting: the phone is put on charge at 23:00 after a day of photos, chats and app updates. The device reports bBackgroundOpStatus = 02h (performance impacted) and the WriteBooster buffer is 70% full.

  1. Screen off, link idle. The host puts the UFS link into Hibern8 between bursts. With fWriteBoosterBufferFlushDuringHibernate set, the device starts draining SLC into TLC.
  2. Android idle maintenance. Once the phone is idle and charging, Android runs maintenance jobs: fstrim sends UNMAP for all free space the file system knows about, and f2fs is asked to clean dirty segments (host GC), discarding the segments it frees.
  3. Device BKOPS. The UNMAPs just turned many "valid" pages invalid, so victims are now cheap. With BKOPS permitted, the device reclaims blocks, does wear levelling and refreshes old data. bBackgroundOpStatus falls back through 01h to 00h.
  4. Morning. Free pool full, SLC buffer empty, map cache warm. The first camera burst of the day runs at full WriteBooster speed with no GC stalls.

Where it goes wrong: an aggressive power policy that fully powers the device down (VCC off) as soon as it is idle leaves no time for BKOPS or the flush. The work is then deferred into foreground GC during the user's next heavy write.

C. The effect of TRIM after deleting a 10 GB video

cheap win

Setting: a user deletes a 10 GB video. Its pages are scattered across many blocks that also hold other live data. Take one typical such block with 384 pages, 230 of them valid (u = 0.60), where 77 of those 230 belong to the deleted video.

Without TRIM, the device would keep faithfully copying the 10 GB of dead video around, GC after GC, until the file system happens to overwrite those exact LBAs. With TRIM, a third fewer copies on this block, 50% more space freed per erase, and the 10 GB also counts as over-provisioning until it is reused. Blocks that held only video pages become entirely invalid and are reclaimed with zero copies.

D. Recording 4K video vs a chat app's database

placement matters

4K video recording

Large sequential writes fill whole blocks with one file. When the clip is later deleted and trimmed, those blocks become 100% invalid together. GC picks them with u = 0, copies nothing, and just erases them. WAF ≈ 1. The simulator's "Sequential" workload shows this.

Messaging app (SQLite + WAL)

Small, frequent overwrites of the same few hundred MB, mixed with cold data such as photos. If hot and cold pages share blocks, every victim still carries cold valid data that has to be copied again and again. With hot/cold separation in the FTL (and f2fs's hot/warm/cold logs), hot blocks die almost completely between GCs, and WAF stays close to 1 for that traffic. Try "Hot/cold" in the simulator.

14 · Summary

TL;DR

  • NAND programs pages but erases whole blocks and cannot overwrite in place, so the FTL writes out of place and leaves stale pages behind.
  • GC reclaims a block by copying its valid pages elsewhere, updating the map, and erasing it. The copies are the cost.
  • WAF = 1 / (1 − u), where u is the valid fraction of victims. Over-provisioning, TRIM, hot/cold separation and good victim selection all exist to keep u low.
  • Foreground GC causes latency spikes. Background GC (BKOPS) is invisible but needs idle, powered time from the host.
  • WriteBooster flushes and HPB map refreshes are both affected by GC, and a full phone hurts all three at once.
  • The host's levers are fBackgroundOpsEn, bBackgroundOpStatus plus the URGENT_BKOPS exception, the WriteBooster flush flags, UNMAP/discard, and simply leaving free space.
Based on the JEDEC UFS specifications (JESD220 family, UFS 3.1 and 4.x), the Linux ufshcd driver and the flash storage literature. Vendor firmware algorithms are proprietary, so device-internal behaviour is described in general terms; timing diagrams are illustrative.
